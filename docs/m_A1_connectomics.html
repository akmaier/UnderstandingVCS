What it does?

Connectomics tries to map the wiring of a system by watching how its parts affect each other. In neuroscience it means reconstructing which neurons connect to which. Here we do the same for the machine's memory. We change one RAM cell, re-run the program, and record which other cells change as a result. Each such dependency is drawn as a directed edge from cause to effect. The full set of edges is the program's data-flow graph, its 'connectome'. The idea is that the pattern of who-influences-whom should reveal the computation, without reading the code. This is a classic move in systems neuroscience: infer function from structure. On the VCS we have the true wiring from the disassembly, so we can check whether the recovered graph is right. The method is attractive because it needs no labels and no model of what the program means. It only needs the ability to perturb and observe. In practice it recovers a graph that looks plausible but contains many edges the real program does not have, because a single perturbation ripples through shared clocks and buffers.

The idea in plain words

A connectome is a wiring diagram: a list of which parts of a system talk to which other parts. Neuroscientists build it for brains. They draw one dot per neuron and one arrow per connection. The hope is simple: if we know who is wired to whom, we can read off how the system computes. One way to find the arrows is to look at the anatomy. Another is to perturb: nudge one unit, watch which other units react, and draw an arrow from the nudged unit to every unit that moved. The result is a directed graph of influence.

For a neural network you already have the anatomy: the weight matrices are the connectome, and they are fully known. Yet nobody claims that printing all the weights explains the network. That is the lesson of Jonas & Kording, who mapped a whole microprocessor and still could not say how it ran a game. On the Atari we ask a sharper question. If we recover the wiring by cheap perturbations, the way it is done in practice, how many of the arrows do we get right? Because the machine can be re-run exactly, we can count every right and every wrong arrow.

How it works on a neural network

Neuroscience origin. The first complete connectome was that of the worm C. elegans: 302 neurons, about 7000 synapses, mapped by electron microscopy in the 1980s. Its behaviour is still not fully explained by that map. Perturbation-based mapping (stimulate one cell, record the others) gives the effective connectivity instead of the anatomical one.

Neural-network analogue. In a network the anatomical connectome is the set of non-zero weights. The perturbation version is what interpretability calls circuit discovery: change one activation \(h_i\), see which downstream activations \(h_j\) change. Write the intervention as \(\mathrm{do}(h_i := v)\) (“force \(h_i\) to the value \(v\), leave everything else to the network”). The recovered edge set is

\[ E_{\text{rec}} = \{\, i\to j \;:\; h_j^{(L)}\big(\mathrm{do}(h_i := h_i+\delta)\big) \neq h_j^{(L)} \,\}, \]

where \(L\) is the latency (how many steps later you look) and \(\delta\) is the size of the nudge. Given a true edge set \(E_{\text{true}}\) you score it like any detector:

\[ P = \frac{|E_{\text{rec}}\cap E_{\text{true}}|}{|E_{\text{rec}}|},\quad R = \frac{|E_{\text{rec}}\cap E_{\text{true}}|}{|E_{\text{true}}|},\quad F_1 = \frac{2PR}{P+R}. \]

Toy example. Three units in a chain, each copying the previous one with a one-step delay: \(a \to b \to c\). Nudge \(a\) and look one step later: only \(b\) moved. Nudge \(b\): only \(c\) moved. So \(E_{\text{rec}} = \{a\to b,\; b\to c\}\). Now look many steps later instead: nudging \(a\) moves \(b\) and \(c\). The long-horizon truth is \(E_{\text{true}} = \{a\to b,\; b\to c,\; a\to c\}\). Then \(P = 2/2 = 1\), \(R = 2/3\) and \(F_1 = 0.8\). Make it harder: let \(b\) copy \(a\) only when \(a > 100\). With \(a = 50\) and a nudge of \(+17\), the gate never opens and even \(a\to b\) is missed. A single small nudge with a short wait sees only part of the wiring.

Recipe

  1. Choose the units (here: candidate RAM bytes) and freeze the system in one state.
  2. Record a baseline: let the system run unperturbed for \(L\) steps and store every unit's value.
  3. For each unit \(i\): restore the frozen state, apply one perturbation \(\mathrm{do}(i := \text{base}_i+\delta)\), run \(L\) steps.
  4. Draw an arrow \(i\to j\) for every unit \(j\) whose value now differs from the baseline. Ignore the self-arrow \(i\to i\).
  5. Build the reference graph the same way but exhaustively (several values, full horizon), or take it from the known anatomy.
  6. Compare the two edge sets: precision, recall, \(F_1\), and the graph-edit distance (number of wrong plus missing arrows).

From a neural network to the Atari

The neuronOne candidate RAM byte. The VCS has 128 bytes of working memory (RAM). Each game's candidate list (e.g. ball x, paddle y, score) comes from published RAM annotations (OCAtari / AtariARI).
The synapseA data-flow edge \(i\to j\): the game program (the ROM, the read-only cartridge code) reads byte \(i\) and, directly or through other bytes, writes a value into byte \(j\).
The stimulation electrodeintervene_ram!: overwrite one RAM byte in the emulator at frame \(f^*\). A frame is one 1/60 s video picture, the unit of game time.
The recordingA full snapshot of RAM (and screen) after re-running the bit-exact emulator jutari from that frozen state.
The true connectomeThe oracle graph: the same probe done exhaustively (three values, full 15-frame horizon). Each probe is a real re-run of the real ROM, so every edge in it is a true causal dependency.

How we apply it to the VCS

The runner A1_connectomics.jl does the whole experiment on one frozen game state. That state is shared with every other method in the study:

  1. The state. The emulator boots the cartridge (60 no-op frames plus 4 reset frames, the same boot as the C++ reference), then plays 90 frames of seeded random joystick input (18 possible actions, seed 0). That frame is \(f^*\). The 15 frames after it are the horizon. A cause-density gate checks with the oracle that at least four candidate causes really move the screen and records whether the state passed, so a frozen title screen is flagged. Two fresh boots must give byte-identical RAM and screen, or the runner refuses to score.
  2. The recovered graph (method under test). For each candidate byte \(i\) the runner copies the frozen machine, adds 17 to byte \(i\) (wrapping at 256), steps one frame, and draws \(i\to j\) for every candidate byte \(j\) that differs from an unperturbed one-frame run. One value, one frame: a thin, realistic probe.
  3. The true graph (oracle). The same loop, but byte \(i\) is set to each of \(0\), base\(+17\) and base\(+37\), and the machine runs the full 15 frames. An edge exists if any of the three values changes \(j\) at the end. Note what this truth is: a measured total-effect graph over the horizon. It includes indirect paths (\(a\to b\to c\) also counts as \(a\to c\)), exactly like the toy example. It is measured by re-running the ROM, not parsed from the disassembly listing.
  4. Scores. Precision, recall, \(F_1\) and graph-edit distance over the off-diagonal edges. A positive control runs the oracle procedure as if it were the method; it must score a perfect \(F_1\), which proves the scorer can reward a correct graph.
  5. Generalisation probe. The runner also builds a true graph from base\(+37\) alone, a value the recovery never used, and checks how well the recovered graph predicts it (edge agreement). A minimality term divides the number of true edges by the number of claimed edges.

Why the gap? The VCS program updates many bytes only on certain frames, behind comparisons and timers. A one-frame wait misses every influence that takes longer to arrive. A single nudge of \(+17\) misses every influence that only fires for other values. And an effect that shows up after one frame but is undone by frame 15 becomes an arrow the truth does not have. The method sees a small, partly wrong slice of a richly connected machine.

Reading the result

The figure shows the game frame and two square matrices over the same candidate bytes. Rows are the cause byte, columns the effect byte, and a bright square is an arrow. The left matrix is the oracle's true graph, the right one the recovered graph. The diagonal (a poked byte changing itself, unless the program overwrites it) is not scored. Read the error as the squares that are bright in one matrix but dark in the other. In Pong the true graph has whole bright rows, because the score bytes and the ball bytes reach many other cells within 15 frames. The one-frame recovery is empty off the diagonal. It misses the wiring rather than inventing it, so recall collapses and \(F_1\) lands at the bottom of the battery.

Pitfalls

  • Latency decides the answer. A one-step readout finds only direct, fast edges. A long readout finds every indirect path. Neither is “the” connectome; say which one you mean.
  • One perturbation value is not enough. Programs (and ReLU networks) are full of thresholds. A nudge that does not cross the threshold reports no edge, even though a different value would.
  • Transient effects create false arrows. A change that appears one frame later but is overwritten before the horizon counts as an edge for the method and not for the truth.
  • Wiring is not function. Even a perfect graph does not say what is computed. The worm's complete connectome did not explain its behaviour, and our oracle graph does not explain Pong.
  • Our truth is a total-effect graph, measured at one state. It is not the static read/write graph of the whole program. Another game state can light up other edges.

How it's scored

The score is a data-flow-graph F1 against the true read/write graph from the disassembly. An edge means that perturbing one RAM cell changes another. We build the recovered graph by single-shot perturbation and compare its edges to the true edges, taking the harmonic mean of precision, the fraction of recovered edges that are real, and recall, the fraction of real edges recovered. Faithfulness for this method is that edge F1: a graph-valued explanation is graded as a graph, not as a heat-map. The comparison is always against the intervention oracle's true wiring, never against another method. The hard part is that a single perturbation ripples through shared clocks and buffers, so the recovered graph contains many edges the real program does not have. Precision suffers, and the F1 stays low. There is no separate position hard-case here, because the method never claims a sprite position; it claims a wiring diagram. The audit box below reports the actual F1, aggregated across the scored games, so no single game dominates. Read the recovered-versus-true graph as the error: every edge in one panel but not the other is a mistake the metric counts.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.

content-F and position-F are n/a for this method. The content-vs-position split applies only to pixel-attribution methods — those that produce an attribution map over the framebuffer, whose score can be read separately on the smooth content outputs and the discrete position outputs (where the naive gradient is provably zero). This method does not attribute to a pixel output; it is graded by its own fidelity metric (dataflow_graph_F1_vs_oracle), reported as the F column, so there is no content or position regime to separate.

Call stack — how it runs on jutari / jaxtari

The path from this method's runner (run_game) into the bit-exact VCS substrate, and the computation it involves. Every step links to the exact source on main. From callstack_phaseA.json.

Applied on the substrate

  1. assemble the shared gameplay-state testbed (seeded random-action stream, bit-exact checkpoint at f*, cause-density gate) — build_a1_shared_state(game) -> build_shared_testbed(game; ...) runner
  2. build_shared_testbed definition: booted checkpoint + shared n_changed_px output + cause-density gate — function build_shared_testbed(game; ...) runner
  3. cause-density gate scores each cause via the injected oracle run_intervention and counts |Delta_y|>floor — cause_density = count(>(floor), deltas) runner
  4. boot the real ROM and deterministically replay to the intervention frame (runner-local boot_replay) — checkpoint = boot_replay(spec, actions, target_frame) runner
  5. fresh env with xitari-parity boot (60 NOOP + 4 RESET) inside boot_replay — env_reset!(env; boot_noop_steps=60, boot_reset_steps=4) runner
  6. step the real emulator one frame per action — env_step!(env, Int(actions[i])) jutari
  7. read the 128-byte RIOT RAM out of the console — get_ram(env) jutari
  8. snapshot RAM+screen at the target frame (state to run the graph on) — at_target = continue_from(checkpoint, Int[]) runner

The computation

  1. the RECOVERED data-flow graph (method under test): single cheap do(i:=base+17), 1-step latency, edge i->j iff cell j differs from baseline — recovered_dataflow_graph(checkpoint, tail, cands, at_target; delta=17, latency=1) runner
  2. the TRUE data-flow graph (ground truth): exhaustive do-set {0, base+17, base+37} at full horizon, edge i->j iff cell j changes for ANY value — true_dataflow_graph(checkpoint, tail, cands, at_target) runner
  3. each edge probe intervenes on a RAM byte then re-runs the tail (uses intervene_ram!) — intervene_continue(checkpoint, c.ram_index, v, tail) runner
  4. score recovered vs true adjacency: precision/recall/F1/graph-edit-distance over off-diagonal edges — score_graph(rec_graph, true_graph) runner

Scored against the exact intervention oracle Δy(u): run_intervention(checkpoint, actions, target_frame, horizon, cause).
