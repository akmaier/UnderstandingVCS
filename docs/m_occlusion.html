Occlusion

Zeiler & Fergus 2014

← back to the method catalogue

What it does?

Occlusion is the most direct attribution method. It hides part of the input, re-runs the system, and measures how much the output changes. A region whose removal changes the output a lot is judged important; a region whose removal does nothing is judged irrelevant. Sliding the occluder over the whole input produces an importance map. For images this means graying out a patch and watching the class score drop. The reason occlusion is powerful is that it is really a coarse intervention: it does not model sensitivity, it actually changes the input and observes the real response. We apply it to the VCS by setting each candidate cause, a RAM cell or register, to an occluded value, re-running the bit-exact program, and recording the change in the output. Because this is a genuine do-operation on the real machine, it tracks the intervention oracle closely, and it works even on a sprite's position where every gradient method fails. Its only weakness relative to the exact oracle is that it perturbs at the granularity of the occluder and can miss fine or joint effects. Occlusion is therefore the bridge between the gradient family and the truly causal methods, and it is among the most faithful attribution methods precisely because it perturbs the real system.

The idea in plain words

A network looks at a photo and says “dog: 92 %”. Instead of asking calculus questions, you can simply cover part of the photo with a grey square and run the network again. If the dog score drops to 30 %, the covered patch mattered. If it stays at 92 %, it did not. Slide the square across the whole photo, write down the drop at every position, and you get a heat-map. That is occlusion: hide one part, re-run, measure the change.

Occlusion is a black-box method. It never opens the network. It needs no gradients and no weights, only the ability to feed in an input and read the output. That makes it slow (one full forward pass per patch) but very honest: it measures what the model actually does when a part is removed, not a local approximation of it. It is the simplest member of the perturbation family (RISE, LIME, KernelSHAP, extremal perturbation), which all work by changing the input and re-running the model.

How it works on a neural network

Write the network as \(y = f(x)\) with input \(x = (x_1,\dots,x_n)\). Pick a baseline value \(b\) that stands for “absent” (grey, black, zero, the dataset mean). Let \(x_{[i \leftarrow b]}\) be the input with part \(i\) replaced by the baseline. Occlusion gives part \(i\) the score

\[ O_i(x) \;=\; \big|\, f(x) - f(x_{[i \leftarrow b]}) \,\big| . \]

For images, “part \(i\)” is a square patch, and the square slides with some stride. The patch size and the baseline are both choices; the map changes when you change them. Cost: one forward pass for the intact input plus one per part.

Toy example 1 (it works). Let \(f(x_1,x_2,x_3) = 4x_1 + x_3\) at \(x = (1,1,1)\), baseline 0. Then \(f(x) = 5\). Occluding \(x_1\) gives 1 (score 4), occluding \(x_2\) gives 5 (score 0), occluding \(x_3\) gives 4 (score 1). The map \((4,0,1)\) is exactly right.

Toy example 2 (redundancy). Now let \(f = \max(x_1, x_2) + x_3\) at \(x=(1,1,1)\), so \(f(x)=2\). Occlude \(x_1\): \(\max(0,1)+1 = 2\), score 0. Occlude \(x_2\): also score 0. Occlude \(x_3\): score 1. Occlusion says \(x_1\) and \(x_2\) are irrelevant. Yet occluding both gives \(f = 1\): together they matter as much as \(x_3\). Each one is a backup for the other, and a one-at-a-time probe cannot see a backup. Remember this blind spot; KernelSHAP fixes it.

Recipe

  1. Choose the output \(y\) to explain and a baseline value that means “absent”.
  2. Run the model once on the intact input and record \(y(x)\).
  3. For each part \(i\): copy the input, set part \(i\) to the baseline, run the model, record \(y(x_{[i\leftarrow b]})\).
  4. Score part \(i\) by \(|y(x) - y(x_{[i\leftarrow b]})|\).
  5. Display the scores as a heat-map (or, here, as one bar per candidate cause).

How we apply it to the VCS

On the VCS, occlusion is almost embarrassingly direct. The game is stopped at frame \(f^*\) (after 90 frames of seeded random play) and the machine is saved as a checkpoint. Then, for each candidate cause \(u\):

  1. deepcopy the checkpoint (a full copy of CPU, RAM, TIA and RIOT state);
  2. occlude! the cause: intervene_ram!(env, idx, 0) for a RAM byte, intervene_tia!(env, reg, 0) for a TIA register, nothing for the joystick;
  3. replay the same recorded 15 actions on the real ROM with env_step!;
  4. read \(y\) and store \(|y(\text{occluded}) - y(\text{intact})|\).

That is one real-emulator re-run per cause, plus one intact run. No surrogate, no gradient, no learned model. Because it only reads the output after a real run, it works just as well on the position output, where the VCS places sprites by timing and every gradient is exactly zero.

How is this different from the oracle? Occlusion is a coarse oracle. The oracle's cause list contains, for every candidate RAM byte, two interventions: ram[i]:set (base value + 17) and ram[i]:occlude (value 0). For the occlude-mode entries, occlusion runs exactly the same experiment as the oracle and gets exactly the same number. The disagreements come from the rest: occlusion gives the set entry of a byte the same score as its occlude twin (it only knows one direction, “to zero”); it sets the background-colour register to 0 where the oracle sets it to white; and it gives the joystick cause zero, because “absent” leaves the action stream untouched while the oracle forces a RIGHT press. So we expect a high but not perfect agreement, and that is what the runner checks (it asserts a positive correlation on the core games, never a perfect one).

The scoring then ranks causes by their occlusion score and runs deletion/insertion curves on the real machine: occlude the top-1, top-2, … causes together and watch \(y\) move.

Reading the result

Each cause has two bars: the occlusion score and the oracle's true effect. Look at the pairs of :set / :occlude causes of the same byte. Occlusion always gives the twins the same height, while the oracle may not. The :occlude bars should match the oracle exactly. The joystick bar is zero for occlusion by construction. Expect the tallest bars to line up with the oracle on both the content and the position output. This is the clearest contrast with the gradient family, whose position-output maps are flat.

Pitfalls

  • Single masking misses backups. If two causes can each do the job alone (toy example 2), occluding either one changes nothing. Occlusion then calls both irrelevant. Joint effects need joint masking (RISE, KernelSHAP) or a search (extremal perturbation).
  • The baseline is a choice. “Absent” = 0 is arbitrary. A byte whose current value is already 0 cannot be occluded at all and always scores 0, however important it is.
  • Off-distribution inputs. On images a grey square is something the network never saw during training (Hooker et al.). On the VCS a zeroed byte is a valid machine state the program will run, but possibly one the game never reaches in normal play.
  • Granularity. The map is only as fine as the parts you hide: patch size on images, the candidate cause list here. A cause that is not on the list gets no score at all.

How it's scored

The score is the Pearson correlation of the occlusion map with the oracle's exact causal map, reported raw, and the grading is always against the intervention oracle. Occlusion is itself a coarse intervention: we set each candidate cause to an occluded value, re-run the bit-exact program, and record the change in the output. Because that is a genuine do-operation on the real machine, its map tracks the oracle closely, and it is among the most faithful attribution methods. Crucially, there is no sprite-position collapse here. Where the gradient family scores zero on a discrete position output, occlusion still works, because perturbing and re-running does not depend on a derivative. So its position-regime faithfulness stays well above the gradient methods', and its all-regime faithfulness is the highest among the attribution methods. Its only shortfall relative to the exact oracle is granularity: it perturbs at the size of the occluder and can miss fine or joint effects that the oracle captures exactly. The audit box reports the measured all-regime faithfulness across the 44 scored games. Occlusion is the clearest attribution-side evidence that a method is faithful exactly when its mechanism is a valid intervention on the real system.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.
