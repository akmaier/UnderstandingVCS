Attribution / edge patching

Nanda 2023; Syed et al. 2023

← back to the method catalogue

What it does?

Attribution patching is a fast, gradient-based approximation to activation patching. Exact patching requires a separate re-run for every internal value tested, which is expensive on a large network. Attribution patching instead uses a first-order, linear estimate: it multiplies the gradient at each site by the change that patching would apply, to predict the patch's effect in a single backward pass. This lets researchers screen thousands of sites at once, at industrial scale, and only re-run the exact patch on the promising ones. We apply it to the VCS by forming the gradient-linear estimate of each site's patch effect and comparing it to the exact effect the oracle measures. The comparison is unusually clean here because we have the exact answer for every site. The linear surrogate keeps the edges precise: it is usually right about which dependencies exist, because a real edge tends to have a non-zero gradient. What it gets wrong is the size of an edge, since the true relationship is not linear, so its numerical agreement with the exact patch is only partial. Attribution patching is therefore a good cheap screen with a measurable error, and the VCS lets us quantify exactly how much accuracy the approximation trades away for its speed.

The idea in plain words

Activation patching is the gold standard of mechanistic interpretability, but it is slow. You need one extra forward pass for every component you test. A large language model has millions of neurons and thousands of attention heads at every token position, so exact patching of all of them is out of reach. Attribution patching is the shortcut. It predicts the effect of every patch at once from a single forward and backward pass.

The trick is the oldest one in calculus: near a point, a smooth function looks like a straight line. If you know the slope of the output with respect to an activation (the gradient), and you know how far the patch would move that activation, then slope × distance is a guess for how far the output moves. That guess is a first-order Taylor approximation. It is exact when the output is linear in the activation, and wrong when it is not. On the VCS we can measure the exact patch effect for every site, so we can see precisely how much accuracy the shortcut trades for its speed.

How it works on a neural network

Use the notation of activation patching: clean input \(x\), corrupted input \(\tilde x\), component \(\ell\) with clean activation \(a = a_\ell(x)\) and corrupted activation \(a' = a_\ell(\tilde x)\). The exact patch effect is \(\Delta_\ell = y(x \mid a_\ell := a') - y(x)\). Attribution patching replaces it with

\[ \widehat{\Delta}_\ell \;=\; \left.\frac{\partial y}{\partial a_\ell}\right|_{x} \cdot \,(a' - a). \]

The gradient for all components comes from one backward pass on the clean run; the \(a' - a\) terms come from one cached corrupted run. That is three passes in total, instead of one per component. Edge attribution patching applies the same estimate to a connection between two components (the sender’s change times the receiver’s gradient), so it can score every edge of the computational graph cheaply.

Toy example. Let \(y = a^2\) with clean \(a = 1\). The slope is \(2a = 2\).

  • Small patch \(a' = 1.1\): estimate \(2 \times 0.1 = 0.2\); truth \(1.21 - 1 = 0.21\). Close.
  • Large patch \(a' = 4\): estimate \(2 \times 3 = 6\); truth \(16 - 1 = 15\). Badly off in size, but the sign is right.
  • Patch at a flat point, clean \(a = 0\), \(a' = 3\): slope \(0\), estimate \(0\); truth \(9\). The estimate misses the effect completely.

The first two cases are why attribution patching is good at which components matter but poor at how much. The third is the dangerous case: a real effect hidden behind a zero gradient, just like saturated attention or a dead ReLU.

Recipe

  1. Run the corrupted input once and cache every activation \(a'_\ell\).
  2. Run the clean input forward, caching \(a_\ell\), and backward from the metric \(y\) to get every \(\partial y/\partial a_\ell\).
  3. For each component, compute \(\widehat\Delta_\ell = \partial y/\partial a_\ell \cdot (a'_\ell - a_\ell)\) (a dot product for vector activations).
  4. Rank components by \(|\widehat\Delta_\ell|\) and keep the top ones.
  5. Verify the shortlist with exact activation patching; the estimate is a screen, not a verdict.

How we apply it to the VCS

The runner is built on top of the activation-patching harness. It uses the same shared gameplay checkpoint, the same outputs and the same patch list: donor patches from LEFT/RIGHT runs, directed base+17 patches on every candidate byte, and one background-colour patch.

  1. The slope. For each site the runner writes \(a+1\) and \(a-1\), re-runs 15 frames each, and divides the difference by 2. At 0 or 255 it uses a one-sided difference. This is the program’s own local derivative, measured on the real machine. It is not a Zygote backward pass. For a single-frame content read the two coincide, but the finite difference also works across 15 frames of discrete code, where autodiff gives no useful answer.
  2. The estimate. \(\widehat\Delta = \text{slope} \times (a' - a)\) for every (site, output) pair.
  3. The truth. The exact patch: write \(a'\), re-run, read the outputs.
  4. Scores. Pearson correlation of estimate vs truth over all cells, mean and relative error, edge precision/recall (does the estimate fire where the truth fires?), and the fraction of active edges where estimate and truth agree exactly (the “linear regime”).
  5. Positive control. A byte read back at the patch frame itself is perfectly linear, \(y(a) = a\). For it the estimate must equal the truth for steps of 1 to 32. This proves the wiring is right, so any error elsewhere is the program’s nonlinearity.
  6. Position gradient. Because this is a gradient method, the runner also reports the naive Zygote gradient of the screen-position output (identically zero) next to the bilinear-sampler gradient, which restores a non-zero value.

Note one honest consequence. On a network the gradient is nearly free. Here each slope costs two re-runs, so the VCS version is not cheaper than exact patching. It is run to measure the approximation error, not to save compute.

Reading the result

Expect the estimate to agree with the truth on which edges exist far better than on their size. Small donor patches and single-frame reads sit in the linear regime and match closely. Large directed patches, bytes that wrap at 255, and bytes the game recomputes each frame break linearity, and the scatter of estimate vs truth spreads out. The correlation is therefore good but clearly below the exact method, and the positive control shows the gap is the program’s fault, not the harness’s.

Pitfalls

  • Large patches are not small. Taylor expansion holds near the clean point. A patch that moves an activation far (here, base+17) can land in a region the slope knows nothing about.
  • Zero gradient, real effect. Saturated softmax, dead ReLUs or a threshold in the program give slope 0 and hide a large true effect. AtP* documents this for attention in LLMs.
  • Wrap-around and thresholds. VCS bytes are 8-bit: 250 + 17 wraps to 11. Comparisons and branches make the output piecewise constant. Both break the linear model.
  • Cancellation. Summing estimates over many components or positions can cancel positive and negative terms that are each large.
  • Use it as a filter. The method is designed to shortlist candidates for exact patching, not to replace it.

How it's scored

The score is the Pearson correlation between the gradient-approximate patch effect and the exact patch effect from the oracle. The grading is always against the intervention oracle. Attribution patching forms a first-order, linear estimate of each site's patch effect in a single backward pass, so we can compare that estimate directly to the exact effect the oracle measures at the same site. Faithfulness for this method is that correlation, and it is good but not perfect, because the true relationship is not linear. The linear surrogate keeps the edges precise: it is usually right about which dependencies exist, since a real edge tends to have a non-zero gradient, so edge precision and recall stay high. What it gets wrong is the size of an edge, which is why the numerical agreement with the exact patch is only partial. There is no sprite-position collapse framed as such here, because the method is scored on internal patch effects rather than on a rendered position; but its gradient origin is exactly why it approximates rather than matches. The grading is always against the oracle. The audit box reports the measured triad, so the correlation is an average across the scored games, quantifying how much accuracy the fast approximation trades away for its speed.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack.
