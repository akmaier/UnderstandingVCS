What it does?

A tuning curve measures how strongly a unit responds to some variable. In neuroscience one plots a neuron's firing rate against, say, the angle of a bar, and a sharp peak is read as the neuron being 'tuned' to that feature. We build the same curves for RAM cells. For each cell we plot its value against a game variable and against screen luminance, then measure how strongly the cell tracks each one. A cell that closely follows a game variable is called tuned to it. The intuition is that a strongly tuned cell must encode that variable and therefore drive the behaviour. This is one of the workhorses of systems neuroscience. On the VCS it is actively misleading. Many cells co-vary with the beam clock and the frame counter, so apparent tuning is cheap and common. A cell can track a game variable perfectly while playing no causal role in producing it. The method thus flags cells that look meaningful but are not, which is exactly the trap we set out to measure. It is the same present-versus-used problem that also defeats linear probing.

Each point is a RAM cell: its true causal importance (x) against its tuning strength to a game variable (y). Red points are strongly tuned yet not causal — the trap the metric measures. The idea in plain words

Put an electrode next to one neuron in a cat's visual cortex. Show the cat a bar of light at different angles. At one angle the neuron fires a lot; at others it is quiet. Plot firing rate against angle and you get a bump: the neuron's tuning curve. A sharp bump makes the neuron selective, or “tuned”, to that angle. Hubel and Wiesel won a Nobel prize for such curves. The tempting conclusion is that the neuron encodes the angle and that the brain uses it to see.

Deep learning does the same thing under other names: finding the “cat neuron”, the “edge detector” in layer 1, or a unit that lights up for one class. The method is purely observational. It watches a unit and a variable change together; it never asks whether the unit is needed. On the VCS we can check that second question with the oracle. We find that many strongly tuned bytes play no causal role at all. Being correlated with a variable and being used to produce behaviour are different things.

How it works on a neural network

Neuroscience origin. A tuning curve is the mean response \(r_i(s)\) of unit \(i\) as a function of a stimulus variable \(s\) (bar angle, sound pitch, head direction). Its sharpness is often summarised by a selectivity index. The extreme form is the “grandmother cell” that fires only for one person.

Neural-network analogue. Network dissection (Bau et al.) measures how well the activation map of a unit overlaps a labelled concept (“dog”, “wood”). Class-selectivity indices compare a unit's mean activation on its favourite class with the others. A simple, general version is the absolute Pearson correlation between a unit's activation over many inputs and a variable \(g\):

\[ s_i \;=\; \max_{g}\; \big|\rho\big(x_i(t),\, g(t)\big)\big|,\qquad \rho(x,g) = \frac{\operatorname{cov}(x,g)}{\sigma_x\,\sigma_g}. \]

A unit is strongly tuned if \(s_i \ge \tau\). Leavitt & Morcos then ablated highly selective units and found that removing them often did not hurt, and sometimes helped: selectivity is a poor guide to importance.

Toy example. A game runs for 10 frames, \(t = 1,\dots,10\). The ball moves right at a steady speed: \(\text{ball\_x}(t) = 20 + 2t\). A separate byte is a frame counter: \(\text{timer}(t) = t\). The timer is never read when the ball is drawn. Still, \(\rho(\text{timer}, \text{ball\_x}) = 1\) exactly, because both are straight lines in \(t\). The tuning method calls the timer perfectly tuned to ball position. If you overwrite the timer, the ball does not move differently. In the language of statistics, the shared driver \(t\) is a confounder: it makes two unrelated things move together.

Recipe

  1. Record a long trajectory: the value of every unit and every candidate variable at every time step.
  2. For each unit and each variable, compute a tuning statistic (here: \(|\rho|\) over time).
  3. Take the unit's selectivity \(s_i\) as its best tuning over the variables, leaving out the unit itself.
  4. Flag units with \(s_i \ge \tau\) as strongly tuned (\(\tau = 0.7\) here).
  5. Ask an independent causal test which units actually matter (here: the intervention oracle).
  6. Report the spurious-tuning rate: the share of strongly tuned units that are not causal.

How we apply it to the VCS

The runner A3_tuning.jl combines one observational part (the method) and one interventional part (the truth) for each game.

  1. Shared state. The cartridge (the ROM) is booted with the game's own settings, then played for 90 frames of seeded random joystick input; that frame is \(f^*\). Two fresh replays must match byte for byte. An oracle gate checks that enough causes move the screen.
  2. Recording. record_parity_trajectory steps the emulator frame by frame for 150 frames along the same input stream (no-op after the 105 gameplay frames) and stores the 128 RAM bytes and the full screen after every frame. This is the “electrode recording”.
  3. Tuning. For each candidate byte the runner correlates its time series with (a) every other candidate byte's time series and a raw score byte, (b) mean screen luminance, and (c) the frame index. The byte's own column is excluded, since a byte trivially correlates with itself. Selectivity is the maximum over (a).
  4. Oracle. For each candidate byte, three interventions at \(f^*\), each followed by a real 15-frame re-run. The causal importance is the largest number of screen pixels that differ from the unperturbed run. A byte is causal if that number is above zero.
  5. Scores. The spurious-tuning rate (strongly tuned but not causal), for game variables and for luminance. The triad: F is the Spearman rank correlation between selectivity and oracle importance; S correlates selectivity with the effect of the held-out base\(+37\) intervention alone; M compares how many bytes the method names with how many truly matter. A positive control scores the oracle against itself.

Why the trap is so easy to fall into on the VCS. Everything in a game is locked to the 60 Hz frame clock. Timers, animation counters and positions of moving objects all change in step with it, so over a short window many bytes look like straight lines in time and correlate strongly with each other. Some of those bytes are also never used for what reaches the screen within 15 frames. The game variables themselves are other RAM bytes, not hand-measured quantities, so a “tuned” pair may simply be two outputs of the same routine.

Reading the result

The figure is a scatter plot with one dot per candidate byte. The x-axis is the oracle's true causal importance, the y-axis the byte's tuning strength to a game variable. Red dots are spurious: strongly tuned (high on the y-axis) yet at zero on the x-axis. Green dots are genuine. If tuning were a good guide, the dots would rise from bottom-left to top-right. In Pong the top-left corner is occupied: bytes that track a game variable almost perfectly but do not change the screen when overwritten. Also look at the bottom-right: causal bytes, such as a score byte that does not change during the window, show no tuning at all. Tuning misses them as well.

Pitfalls

  • Present is not used. A unit can carry information about a variable without the system ever reading it. This is the same trap that defeats linear probing.
  • Shared drivers. Anything that changes steadily with time (a clock, a scrolling position) correlates with everything else that does. Always include a clock or time control.
  • Constant causes are invisible. A byte that is crucial but does not change during the recording has zero variance, so zero correlation, and is never called tuned.
  • Threshold and window. The rate depends on \(\tau\) and on which 150 frames are recorded. A different phase of play can tune different bytes.
  • Linear only. Pearson's \(\rho\) sees straight-line relations. A byte that encodes a variable through a table or a bit mask can look untuned.

How it's scored

The score is a spurious-tuning rate: the fraction of cells that are strongly tuned to a game variable yet are not among the oracle's causal cells. We first find the cells whose value tracks a game variable strongly, then ask the intervention oracle which of those cells actually cause the output. A tuned cell that is not causal is a false positive, and the spurious-tuning rate counts them. Faithfulness is one minus that rate, so a method that only flags true causes scores high and a method that flags many non-causal cells scores low. On the VCS the rate is high, because many cells co-vary with the beam clock, so tuning is cheap and often unrelated to causation. This is the same present-versus-used trap that also defeats linear probing: a cell can carry a variable without the program using it. The grading is always against the oracle. There is no sprite-position hard-case here, because the output is a tuning judgement, not a coordinate. Because per-game correlations for this family can go negative, the aggregate clips each per-game value at zero before averaging, so a method with no real signal lands near zero rather than at a spurious floor. The audit box reports the aggregated faithfulness.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.

Results per game

This method's faithfulness on each of the 42 scored games (all-regime F; this method has no content-vs-position split (see the note below)). Click a header to sort. Every number is read from site_data.json (methods.A3_tuning.per_game).

content-F and position-F are n/a for this method. The content-vs-position split applies only to pixel-attribution methods — those that produce an attribution map over the framebuffer, whose score can be read separately on the smooth content outputs and the discrete position outputs (where the naive gradient is provably zero). This method does not attribute to a pixel output; it is graded by its own fidelity metric (A3_game_variable_spurious_tuning_rate), reported as the F column, so there is no content or position regime to separate.

M is n/a on 6 of these games. Minimality is M = |U*|/|Û|, the size of the true minimal cause set over the size of the set the method actually names. On a game where the method names nothing (|Û| = 0 — it discovers no circuit, its attribution map is all-zero, or it decodes no cell), that ratio is undefined, so M is left blank rather than scored. The aggregate M is the mean over the 36 games where the method did name a cause set.

S is negative on 12 of these games. Sufficiency asks whether the explanation can predict the outcome of held-out interventions it was not fit on; for this method S is the held-out predictive correlation between its claim and the true effect, so it lies in [−1, 1]. A value near 0 means the explanation predicts no better than the unperturbed output; a negative value means it predicts worse — its held-out claim is anti-correlated with the truth (named yet causally unused). The aggregate S is the mean over the scored games.

Call stack — how it runs on jutari / jaxtari

The path from this method's runner (compute_game) into the bit-exact VCS substrate, and the computation it involves. Every step links to the exact source on main. From callstack_phaseA.json.

Applied on the substrate

  1. assemble the shared gameplay-state testbed + cause-density gate — build_a3_shared_state(game) -> build_shared_testbed(game; ...) runner
  2. build_shared_testbed definition: booted checkpoint + shared output + gate — function build_shared_testbed(game; ...) runner
  3. cause-density gate counts causes with |Delta_y|>floor via the oracle — cause_density = count(>(floor), deltas) runner
  4. record a JutariRecord.Trajectory: step the ROM frame-by-frame and log RAM+screen per frame (the tuning-curve data matrix) — record_parity_trajectory(game, actions) runner
  5. step the real emulator one frame per action while recording — env_step!(env, Int(actions[t])) jutari
  6. read RAM into the trajectory tape each frame — get_ram(env) jutari

The computation

  1. derive game-variable signals (candidate-cell time series) from the trajectory tape — game_variable_signals(traj, cands) runner
  2. derive luminance + frame-clock reference signals — luminance_and_clock(traj) runner
  3. fit tuning curves (method under test): per-cell |Pearson correlation| selectivity to game variables / luminance / clock, self-column excluded — run_a3_tuning(traj, cands, oracle_importance; tau=0.7) runner

Scored against the exact intervention oracle Δy(u): run_intervention(checkpoint, actions, target_frame, horizon, cause).
