Phase C · mechanistic interpretability

Linear probing + control tasks

Alain & Bengio 2017; Hewitt & Liang 2019

← back to the method catalogue

What it does?

Linear probing asks whether a concept can be read out of the state by a simple classifier. A linear probe is trained to predict a concept, say the ball's position, from the internal state; if it succeeds, the concept is said to be 'encoded' there. The well-known danger is that a probe can succeed just because the concept happens to be linearly recoverable, not because the system uses it. Hewitt and Liang's control-task fix addresses this: train a second probe to predict a random label, and report selectivity, the probe's real accuracy minus its accuracy on the random control. High selectivity means the state genuinely encodes the concept rather than the probe memorising it. We apply this on the VCS, training probes for game concepts and subtracting the control-task baseline. The VCS then adds a test no neural network allows: we check, by intervention, whether the program actually uses each decodable cell. It often does not. A cell can be decodable, and pass the control-task check, yet be provably unused when we clamp it and re-run, because the value is present in the state but never causally used within the window. Linear probing is thus our clearest illustration of the present-versus-used gap: decodability shows information is there, but only the intervention oracle shows whether the program relies on it.

The idea in plain words

Does a language model “know” the part of speech of each word? Does a chess network “know” where the king is? A probe is the simplest way to ask. You freeze the network, record its hidden activations, and train a tiny, separate classifier to predict the concept from them. If even a linear classifier succeeds, people say the concept is linearly represented at that layer. Probing is cheap, works on any layer, and has been run on almost every large model.

Two traps make the answer less clear than it looks. First, a probe that is too flexible can memorise labels instead of finding them. Hewitt and Liang's control task fixes that: give the same probe a nonsense labelling and see how well it does anyway. Second, and deeper: a probe tells you a concept is present, that is, readable from the activations. It does not tell you the network uses it. Information can sit in a layer as a by-product, read by no later computation. This page is built around that present-versus-used gap.

How it works on a neural network

Let \(h \in \mathbb{R}^d\) be the frozen activation for one input and \(c \in \{1,\dots,K\}\) the concept label. A linear probe predicts

\[ \hat c = \arg\max_k \,(W h + b)_k , \]

with \(W, b\) fit on labelled examples and accuracy measured on held-out ones. The control task keeps the inputs but replaces the labels: every distinct input type (in NLP, every word) gets a fixed random label. A probe can only score well on that by memorising. The honest number is the selectivity:

\[ \text{selectivity} = \text{acc}_{\text{real}} - \text{acc}_{\text{control}} . \]

Toy example (present but unused). A two-unit hidden layer gets an input number \(n\). Unit \(h_1 = n\) and unit \(h_2 = n \bmod 2\) (the parity). The output is \(y = 2h_1\); nothing ever reads \(h_2\). A probe on \(h_2\) predicts “is \(n\) odd?” with 100 % accuracy, and on a control task it scores only chance, so selectivity is high. A naive reading says “the network computes parity”. Yet setting \(h_2\) to any value leaves \(y\) unchanged: for \(n=3\), \(y=6\) whether \(h_2\) is 0 or 1. Decodable, selective, and causally irrelevant.

Recipe

  1. Record frozen activations and the concept label for many inputs; split into train and test.
  2. Fit a linear classifier (logistic or least-squares, usually regularised) and measure test accuracy.
  3. Build a control task: map each input type to a fixed random label of the same cardinality, and train the same probe on it.
  4. Report selectivity = real accuracy minus control accuracy, not raw accuracy.
  5. To ask whether the concept is used, intervene: remove or change it in the activations and check the output (e.g. amnesic probing).

How we apply it to the VCS

Our runner linear_probing.jl needs labels, because it decodes named concepts. Per game it does this:

  • Data. A 600-frame RAM tape. The first 105 frames follow the shared seeded gameplay stream; the rest continue with NOOP. 600 frames give 420 training rows for 127 inputs, enough that the linear system cannot simply memorise.
  • Hold out the target. To probe cell \(c\), the input is every other byte. Otherwise the probe could copy the answer. So the real question is: is this variable redundantly encoded in the rest of the state?
  • Probe. Labels are 4 equal-width bins of the cell's observed range (empty bins dropped). The probe is a one-vs-rest least-squares classifier with a small ridge penalty (\(\lambda = 0.01\)), solved in closed form. Frames are shuffled with a fixed seed and split 70/30.
  • Control. Every distinct raw byte value gets a random label. Keying on raw values, not on the 4 bins, makes the control genuinely hard: a 4-way random map would be easy to memorise.
  • Decodable. A cell counts as decodable (present) if test accuracy is at least 0.5 and selectivity is at least 0.1.
  • Used? Each probed cell is then cross-checked against the oracle's list of “transient” cells from the DAS run (das_<game>.json). These are cells the program recomputes within the horizon, so writing a new value into them has no downstream effect. A cell that is decodable and transient is counted as decodable-but-not-causal: present, not used.

The headline is mean selectivity over all probeable cells, next to the count of decodable-but-not-causal cells. Note the dependency: if the DAS output is missing, the “used” cross-check is marked as unavailable rather than guessed.

Reading the result

Each bar is one labelled cell: its selectivity (probe accuracy minus control accuracy); red bars are cells the oracle flags as not causally used. Expect most game variables to be decodable above the control. The VCS state is small and full of copies and derived values, so the rest of RAM often predicts a variable well. Then look for the red cells that are still decodable: present but not used. They are the key result: a probe would “find” these concepts, a naive reading would say the program relies on them, and the intervention shows that, within the window, it does not.

Pitfalls

  • Present is not used. The central lesson. A probe answers “can it be read?”. Only an intervention answers “does changing it change the output?”.
  • Probe capacity. A powerful probe can learn the task itself. Use a control task and report selectivity; keep the probe linear and regularised.
  • Neighbouring frames leak. We shuffle frames before splitting, and consecutive frames are nearly identical. Test accuracy can therefore be optimistic compared with a split by time.
  • Binning shapes the task. Four equal-width bins over the observed range are a choice; a different binning changes both accuracies.
  • Redundancy, not location. Because the target cell is held out, a high score means the variable can be inferred from other bytes. It does not say where the program stores it.

How it's scored

The score is the mean selectivity: the probe's accuracy minus the accuracy of a control-task probe trained on a random label, averaged over the labelled cells. The control task follows Hewitt and Liang and guards against a probe succeeding merely because a concept is linearly recoverable. The grading is always against the intervention oracle. Faithfulness for this method is that selectivity, and it is modest, but the deeper finding comes from crossing the probe against the oracle. Concepts are decodable above the control, so the information is present in the state, yet the oracle flags cells that are decodable but never causally used within the window. That is the present-versus-used gap: a value can be read out without the program relying on it. There is no sprite-position hard-case here; the output is a decodability judgement. The grading is always against the oracle, which is strictly stronger than the probe, because the probe asks whether a value can be read while the oracle asks whether changing it changes the output. The audit box reports the measured triad. Linear probing earns a high plausibility proxy on a low faithfulness, which places it in the danger zone and makes it the clearest illustration of decodable-but-unused information.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.

Results per game

This method's faithfulness on each of the 27 scored games (all-regime F; this method has no content-vs-position split (see the note below)). Click a header to sort. Every number is read from site_data.json (methods.linear_probing.per_game).

content-F and position-F are n/a for this method. The content-vs-position split applies only to pixel-attribution methods — those that produce an attribution map over the framebuffer, whose score can be read separately on the smooth content outputs and the discrete position outputs (where the naive gradient is provably zero). This method does not attribute to a pixel output; it is graded by its own fidelity metric (probe_selectivity_vs_causal_use_correlation), reported as the F column, so there is no content or position regime to separate.

M is n/a on 1 of these games. Minimality is M = |U*|/|Û|, the size of the true minimal cause set over the size of the set the method actually names. On a game where the method names nothing (|Û| = 0 — it discovers no circuit, its attribution map is all-zero, or it decodes no cell), that ratio is undefined, so M is left blank rather than scored. Call stack — how it runs on jutari / jaxtari

The path from this method's runner (run_game) into the bit-exact VCS substrate, and the computation it involves. Every step links to the exact source on main. From callstack_phaseC.json.

Applied on the substrate

  1. Boot the real ROM with the xitari-parity reset (60 NOOP + 4 RESET) — env_reset!(env; boot_noop_steps = 60, boot_reset_steps = 4) jutari
  2. Deterministically step the emulator one action per env-frame (drives the RAM-tape recording) — env_step!(env::StellaEnvironment, action::Integer) jutari
  3. Assemble the shared gameplay-state testbed via build_linear_probing_shared_state — build_shared_testbed(game; ... intervene_ram = J.intervene_ram!, run_intervention = O.run_intervention, soft_ram_peek = soft_ram_peek, ...) runner
  4. Freeze byte-exact RAM + screen out of the env at a frame — snapshot(env::StellaEnvironment, frame::Integer) jutari

The computation

  1. Record the per-frame RAM tape (128-byte activations) the probes are trained on — record_ram_tape(game, actions) -> env_step! runner
  2. Train a linear (ridge) probe per RAM cell + control-task selectivity: probe accuracy on the real label vs a random control label — probe_accuracy(Xtr, ytr, Xte, yte, nclass; lambda = RIDGE_LAMBDA) runner
  3. Cross-reference each probed cell with the oracle causal flag (transient/causal cells) so selectivity is scored against real causal use — oracle_transient_cells(game::AbstractString) runner

Scored against the exact intervention oracle Δy(u): run_intervention(checkpoint, actions, target_frame, horizon, cause).
