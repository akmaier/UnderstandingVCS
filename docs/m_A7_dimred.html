A7 · Dimensionality reduction (NMF/PCA)

cf. Jonas & Kording 2017

← back to the method catalogue

What it does?

Dimensionality reduction summarises high-dimensional activity by a few components. Principal component analysis (PCA) finds the directions of largest variance; non-negative matrix factorisation (NMF) finds additive, parts-based factors. Both are standard in neuroscience for turning a large population recording into a handful of interpretable 'latent factors'. We run them on the VCS state tensor, the values of all cells over time, and read off the recovered components. We then match each component to a known signal: the frame or scanline clock, a read/write pattern, the vsync flag, or a game variable. The intuition is that the strongest components should correspond to the machine's real internal signals, so the factorisation recovers the structure without any labels. The method is unsupervised and cheap, which is why it is popular. On the VCS it does moderately well: it recovers most of the known factors, and NMF's non-negativity fits the additive register basis a little better than PCA. But a large fraction of components stay unmatched or mix several true signals into one, so the decomposition is suggestive rather than exact. It finds structure that is genuinely present, without telling us how the program uses it.

The idea in plain words

Modern recordings are huge: hundreds of neurons, or thousands of hidden units, over thousands of time steps. Nobody can stare at that table. Dimensionality reduction compresses it. It looks for a few components: patterns of joint activity that, added together, rebuild most of the table. Each component has a loading (how strongly each unit takes part) and an activation over time (how strongly the pattern is “on” at each step). The hope is that these few latent factors are the system's real internal variables: “arm direction”, “choice”, “ball position”.

Two classic tools are used. PCA (principal component analysis) finds the directions along which the data vary most. NMF (non-negative matrix factorisation) instead rebuilds the data as a sum of non-negative “parts”, which often look more like separate objects. Both are unsupervised: they need no labels. That is their charm and their risk. They find what is large in the data, and large is not the same as important. On the Atari we can check which components match real signals, and whether the bytes they highlight are the ones that actually cause what appears on screen.

How it works on a neural network

Neuroscience origin. PCA, factor analysis and NMF are staples of population analysis (Cunningham & Yu 2014): reduce a recording to a few latent trajectories, then interpret them. Jonas & Kording ran NMF on the transistor activity of a simulated 6502 and found components that tracked the clock and bus activity, not the program's logic.

Deep-learning analogue. Dimensionality reduction of activations: PCA of a layer's activations over a dataset, NMF of CNN feature maps into “concept” parts, or the top singular directions of a residual stream. Arrange the recording as a matrix \(X\) of size \(T\times n\) (time steps × units).

PCA centres each column (subtracts its mean, giving \(X_c\)) and takes the singular value decomposition \(X_c = U S V^\top\). Column \(j\) of \(V\) is component \(j\)'s loading over the \(n\) units; \(X_c V\) gives the activations; the share of variance explained is \(s_j^2/\sum_k s_k^2\).

NMF requires \(X\ge 0\) and finds \(W\ge 0\) (\(T\times r\), activations) and \(H\ge 0\) (\(r\times n\), loadings) that minimise \(\lVert X - WH\rVert_F\). The Lee–Seung multiplicative updates keep everything non-negative:

\[ H \leftarrow H \odot \frac{W^\top X}{W^\top W H}, \qquad W \leftarrow W \odot \frac{X H^\top}{W H H^\top} . \]

Toy example. Record two bytes over four frames. Byte A is a frame counter: \((0, 64, 128, 192)\). Byte B is the score: \((0, 0, 1, 1)\). Byte A has variance 5120; byte B has variance 0.25. PCA's first component points almost entirely at A and explains more than 99.99 % of the variance. The score barely registers. Now suppose the score is what the screen shows and the counter only drives a blink. The top component has picked the loudest byte, not the causal one. Variance is a statement about the data, not about cause.

Recipe

  1. Record the population as a \(T\times n\) matrix \(X\) (here: 128 RAM bytes over \(T\) frames).
  2. PCA: centre the columns, take the SVD, keep the variance fraction of each component.
  3. NMF: pick a rank \(r\), run multiplicative updates from a seeded random start, and order components by energy.
  4. For each leading component, ask whether it matches a known variable (its loading sits on one variable) or a known signal (its activation tracks it).
  5. Turn the loadings into a per-unit “recovery” score: how strongly the leading components load on each unit.
  6. On the VCS, compare that score with the oracle's true causal importance of each unit.

Latent factorsThe top-5 PCA components and the top-5 of a rank-8 NMF, each with a loading over the 128 bytes and an activation over frames.
Known task variablesThe game's candidate bytes, grouped into variable families (score, ball, enemy, …), plus three structural signals: a frame clock ramp, the population write activity (bytes changed per frame), and a periodic frame-phase wave.
“This component is the choice variable”A matched component: at least half of its candidate-byte loading lies on one family (and candidates carry a real share of the loading), or its activation correlates \(|r|\ge0.5\) with one structural signal.
Importance of a unit (unknown in a brain)The intervention oracle: set the byte to 0 or base+17 at frame \(f^*\), re-run the real ROM for the horizon, count changed screen pixels.

How we apply it to the VCS

The runner A7_dimred.jl does two things: a descriptive match of components to known signals, and an oracle-scored test of whether the components point at causal bytes.

  1. The recording. From the shared gameplay state (seeded random actions, checkpoint at frame \(f^*=90\), 15-frame horizon), a7_record_ram steps the real ROM with env_step! and stores the RAM each frame. The trajectory is 150 frames for most games, continued with NOOP after the gameplay window.
  2. Decompositions. run_pca centres the raw byte values and takes an SVD. run_nmf runs 300 Lee–Seung updates at rank 8 from a seeded random start, then sorts components by energy (the size of each rank-one part \(W_{:,k}H_{k,:}\)). No package is added; both are written out in the file.
  3. Matching. known_signals builds the clock ramp, the write-activity count, and a sinusoid at the dominant autocorrelation period of that count. match_components then labels each of the top-5 components as a game variable, a known signal, or unmatched (purity threshold 0.5). The headline record value is the NMF matched-component fraction.
  4. Causal check. recovery_scores gives each candidate byte a score: its squared loading on the top-5 components, weighted by variance (PCA) or energy (NMF). oracle_importance pokes each candidate byte to 0 and to base+17, re-runs the horizon and counts changed pixels. A third value, base+37, is held out. score_triad gives F (Spearman rank correlation of recovery vs importance), S (Pearson against the held-out effect) and M (the true cause set's size over the named set's size).

Read the match metric carefully. A component that tracks the frame clock counts as “matched”. That is honest bookkeeping (the component is a real signal), but it is the epiphenomenal signal A5 warns about. The triad is what asks whether the components point at causes. Note also that the “frame-phase” wave is a stand-in: per-frame sampling cannot see the real VSYNC pulse, so it is a periodic proxy derived from the data.

Reading the result

The figure shows two bars per candidate byte (Pong): the oracle's true causal importance and the byte's NMF recovery score, both scaled so the largest is 1. A faithful decomposition would give bars of matching height. Expect them not to match. The leading components favour the bytes that vary most, such as a paddle position the oracle calls inert, while bytes that matter but barely change, such as the scores, get almost no recovery. The match metric in the record tells a kinder story: a good share of the leading components match a game variable or a known signal, for PCA and NMF alike. The structure is real; it is just not the same thing as the program's causal story.

Pitfalls

  • Variance is not importance. A wide-ranging counter dominates PCA while a one-bit flag that decides the game barely moves it (the toy example). Raw byte values are not rescaled here, so wide-range bytes weigh more.
  • Components mix variables. Nothing forces one component per true variable. PCA's orthogonality constraint and NMF's additivity both produce blends when variables co-vary.
  • A match is not an explanation. Matching the clock is a correct label for a causally inert signal. Matching a game variable says the variable varies a lot, not that the program uses it here.
  • Arbitrary choices. Rank, number of components kept, purity threshold and NMF seed all change the answer. NMF also has no unique solution.
  • Correlational. Like every recording-only method, it never intervenes. Only the oracle comparison tells you whether a component points at causes.

How it's scored

The score is the fraction of NMF or PCA components that match a known signal or variable. We decompose the state tensor into components, then match each to the machine's known internal signals, the frame or scanline clock, a read/write pattern, vsync, or a game variable, and count the matched fraction against what the oracle marks as important. Faithfulness for this method is that matched-component fraction. It is moderate: the decomposition recovers most of the known factors, and NMF's non-negativity fits the additive register basis a little better than PCA, but a substantial fraction of components stay unmatched or mix several signals into one. A secondary reconstruction-error composite gives NMF a small edge, but on the primary matched-fraction metric the two are close. The grading is always against the oracle, not against another method. There is no sprite-position hard-case here; the output is a set of components. The audit box reports the measured matched fraction across the scored games, so the number is an average over the scored set rather than the best single game.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.

Call stack — how it runs on jutari / jaxtari

The path from this method's runner (compute_game) into the bit-exact VCS substrate, and the computation it involves. Every step links to the exact source on main. From callstack_phaseA.json.

Applied on the substrate

  1. assemble the shared gameplay-state testbed + cause-density gate — build_a7_shared_state(game) -> build_shared_testbed(game; ...) runner
  2. build_shared_testbed definition: booted checkpoint + shared output + gate — function build_shared_testbed(game; ...) runner
  3. cause-density gate counts causes with |Delta_y|>floor via the oracle — cause_density = count(>(floor), deltas) runner
  4. record a (frames x 128) RAM tape by stepping the ROM with A7's per-game settings — a7_record_ram(game, frames, actions) runner
  5. step the real emulator one frame per action while recording — env_step!(env, Int(actions[t])) jutari
  6. read RAM into the tape each frame — get_ram(env) jutari

The computation

  1. PCA (method under test): principal-component decomposition of the RAM tape — run_pca(tape) runner
  2. NMF (method under test): non-negative matrix factorization of the RAM tape into rank components — run_nmf(tape, rank; iters=300, seed=0) runner
  3. match recovered components to known ground-truth signals (scoring) — match_components(method, tape, ...) runner

Scored against the exact intervention oracle Δy(u): run_intervention(checkpoint, actions, target_frame, horizon, cause).
