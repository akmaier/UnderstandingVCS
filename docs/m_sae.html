Sparse autoencoders

Cunningham et al. 2023; Bricken et al. 2023; Templeton et al. 2024

← back to the method catalogue

What it does?

A sparse autoencoder tries to break a tangled state into clean, single-meaning features. It is a small neural network trained to reconstruct the recorded state through a wide but sparsely active hidden layer, so that only a few hidden units fire for any given input. The hope is that each hidden unit becomes 'monosemantic', standing for one human-meaningful concept, which would untangle the superposition thought to hide features inside neural activations. Sparse autoencoders are a central, fast-growing tool in mechanistic interpretability. We train one on the recorded RAM trajectory of the VCS and match its learned features to known, verified game-variable cells. On this small state the reconstruction is nearly perfect and every game-variable cell the SAE is asked to match gets a matching feature. By the metric the field usually uses to claim a feature 'is' a concept, the SAE looks like a complete success. The VCS lets us apply a stronger test. We ablate the matched feature, re-run the real ROM, and ask whether the computation it is supposed to name actually changes. Often it does not: the feature is named but causally unused: clamping it and re-running changes nothing. The sparse autoencoder is therefore our sharpest example of a method that scores well on the standard matching metric while failing the causal test that only a known machine can provide.

The idea in plain words

Look inside a language model and pick one neuron. You will often find it fires for many unrelated things: Python code, the French word for “cat”, and closing brackets. Such a neuron is polysemantic (many meanings). One explanation is superposition: the model wants to store more concepts (“features”) than it has neurons, so it packs them in as overlapping directions in activation space. That works because most features are sparse: in any one input, only a few of them are active, so the overlaps rarely collide.

A sparse autoencoder (SAE) tries to undo the packing. It is a small, separate network trained to rebuild the model's activation vector through a hidden layer with many units, under a penalty that keeps only a few units active at a time. If it works, each hidden unit stands for one concept: it is monosemantic. These units are then called the model's “features”, given names, and used to explain and steer the model. SAEs are among the most widely used tools in interpretability today.

How it works on a neural network

Take an activation vector \(x \in \mathbb{R}^d\) (e.g. the residual stream of a transformer at one token). The SAE encodes and decodes it:

\[ z = \mathrm{ReLU}(W_e x + b_e), \qquad \hat x = W_d z + b_d, \qquad \mathcal{L} = \|x - \hat x\|^2 + \lambda \|z\|_1 . \]

\(z\) is the code (one number per feature). ReLU sets negative values to zero. The first loss term asks for a good reconstruction. The second, an L1 penalty (the sum of absolute values, known from the lasso), pushes most entries of \(z\) to exactly zero. \(\lambda\) trades the two off. Usually the hidden layer is wider than \(d\) (“overcomplete”), so it has room for more features than neurons. Column \(k\) of \(W_d\) is feature \(k\)'s direction in activation space.

Toy example. A model stores 3 features in a 2-D space, at 120° apart: \(u_1=(1,0)\), \(u_2=(-0.5,0.87)\), \(u_3=(-0.5,-0.87)\). An input has only feature 2 on: \(x=u_2=(-0.5,0.87)\). The two raw neurons read \(-0.5\) and \(0.87\): both respond, and each would also respond to the other features. Now an SAE with three hidden units, encoder rows \(u_1,u_2,u_3\) and bias \(-0.4\): the pre-activations are \((-0.5, 1.0, -0.5) - 0.4 = (-0.9, 0.6, -0.9)\), and ReLU gives \(z=(0, 0.6, 0)\). Only unit 2 fires. Three features, cleanly separated, from a 2-D space.

Recipe

  1. Record many activation vectors from the model (one layer, many inputs).
  2. Normalise them, then train the SAE on the reconstruction loss plus \(\lambda\cdot\) L1 of the code.
  3. Check reconstruction quality (fraction of variance explained) and sparsity (average number of active units, \(L_0\)).
  4. Interpret each unit: list the inputs where it fires most, or correlate it with known concepts.
  5. Test causally: set a feature to zero (or clamp it high), decode, put the result back into the model, and see whether the behaviour changes as the feature's name predicts.

How we apply it to the VCS

Our runner sae.jl is a complete SAE pipeline written by hand in Julia (no deep-learning library), applied to the VCS state instead of a transformer.

  • Data. We record the RAM after every frame along the shared gameplay stream (90 seeded random-action frames plus the 15-frame horizon, continued with NOOP; 150 frames for Pong). Each byte is z-scored (mean 0, standard deviation 1). Bytes that never change are set to zero. Every fifth frame is held out for testing.
  • Model and sweep. \(z=\mathrm{ReLU}(W_e x+b_e)\), \(\hat x = W_d z + b_d\), loss = mean squared error + \(\lambda\cdot\)mean\(|z|\). Full-batch gradient descent, 4000 epochs, learning rate 0.5, with the gradients written out explicitly. We sweep the width \(\in\{16,32,64\}\) and \(\lambda\in\{0.01,0.05,0.2\}\) and keep the model with the best held-out reconstruction. Note: these widths are smaller than 128, so the SAE is not overcomplete in raw bytes. But most of the 128 bytes are constant over a short run, so the number of bytes that actually vary is far smaller.
  • Matching. For each known cell that varies, we find the feature whose activation has the largest absolute Pearson correlation with the cell's value over the run. The cell is “matched” if that correlation is at least 0.7. The match rate is the share of varying known cells that get a match. This is the kind of evidence papers use to say “this feature is concept X”.
  • Causal use. This is the test a language model cannot give us. For each matched cell that the oracle says is causal, we encode the RAM at \(f^*\), set its best feature to zero, decode, undo the z-scoring, round to bytes, and write the full 128-byte vector into a copy of the machine. Then we play the 15-frame tail. The effect is the number of screen pixels that differ from the same write without the ablation, so reconstruction error cancels out. We also count decode leakage (how many bytes of the ablated decode differ from the real RAM) and the share of the effect that the target cell alone explains.
  • Controls. One ablated write is replayed through an independent fresh boot and must match the checkpoint path exactly. The oracle's own importance map, scored as if it were the method, must get a perfect rank correlation.

The triad: F is the Spearman rank correlation between each cell's SAE “recovery score” (best feature correlation × decoder weight mass on that cell) and the oracle's importance. S predicts a held-out lesion (base+37) from the same score. M asks whether the cells the SAE highlights are the cells that matter.

Reading the result

Expect two very different pictures side by side. The reconstruction is close to perfect and the match rate is high: almost every known cell has a feature that tracks it. By the usual standard of the field, the SAE has “found the variables”. Then look at the causal-use bars. Ablating a matched feature often moves the screen much less than the oracle says that cell matters, or moves it through other bytes the decoder also touched. The lesson is the gap between named and used: a feature can track a variable perfectly and still not be the handle by which the program's computation runs.

Pitfalls

  • Correlation is not mechanism. A feature that correlates with ball x may also correlate with a frame counter or the paddle. High correlation names a feature; it does not prove the model uses that direction.
  • Decode leakage. Zeroing one feature changes the decoded value of many bytes at once. The observed effect then mixes several variables, which breaks the “one feature, one concept” story.
  • Hyper-parameters shape the dictionary. Width and \(\lambda\) decide how features split or merge. A different sweep can give different “features” on the same data.
  • Interpretable-looking is not evidence. Heap et al. found that standard automated interpretability scores for SAE features look similar on trained and randomly initialised transformers. On the VCS we score against the oracle instead.
  • Small state, easy case. The VCS keeps variables in separate bytes, so there is little superposition to undo. A high match rate here is expected and says little about how SAEs fare on dense LLM activations.

How it's scored

The score is the fraction of sparse-autoencoder features that match a known, verified game-variable cell, together with a causal-use check by ablation. We first measure the matched fraction, how many of the concept cells the SAE was asked to represent get a matching feature, and on this small state that fraction is high. That is the metric the field usually uses to claim a feature is a concept. The VCS then applies a stronger test the audit treats as the real faithfulness: we ablate the matched feature, re-run the real ROM, and ask whether the computation it is supposed to name actually changes. Often it does not, so the causal faithfulness is low even though the matched fraction is high, and the sufficiency can even go negative. This split is the point: a feature can be named yet causally unused. There is no sprite-position hard-case here, because the method is scored on features and their ablation, not on a rendered position. Its plausibility proxy is high, which places it in the danger zone of high plausibility with low faithfulness. The grading is always against the intervention oracle, never against the matching metric alone. The audit box reports the measured triad, so you can read the low causal faithfulness directly.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.

content-F and position-F are n/a for this method. The content-vs-position split applies only to pixel-attribution methods — those that produce an attribution map over the framebuffer, whose score can be read separately on the smooth content outputs and the discrete position outputs (where the naive gradient is provably zero). This method does not attribute to a pixel output; it is graded by its own fidelity metric (feature_variable_matched_fraction), reported as the F column, so there is no content or position regime to separate.

S is negative on 24 of these games. Sufficiency asks whether the explanation can predict the outcome of held-out interventions it was not fit on; for this method S is the held-out predictive correlation between its claim and the true effect, so it lies in [−1, 1]. A value near 0 means the explanation predicts no better than the unperturbed output; a negative value means it predicts worse — its held-out claim is anti-correlated with the truth (named yet causally unused).
