Grad×Input / DeepLIFT

Shrikumar et al. 2017

← back to the method catalogue

What it does?

Grad times Input, in the DeepLIFT family, sharpens plain saliency by multiplying the gradient at each input by the input's own value. The product answers a slightly different question than the bare gradient: not just how sensitive the output is to an input, but how much that input, at its actual value, contributes to the output. DeepLIFT frames this as a difference from a reference, and the multiplication gives the method a completeness-like property, so the attributions sum to the change in the output. For images this tends to produce cleaner, less diffuse maps than raw saliency. We apply it to the VCS by multiplying each cause's gradient by its recorded value and correlating the result with the true causal map. On outputs that flow smoothly into the picture, the input factor concentrates the attribution onto the genuine causal byte and improves on plain saliency. On a sprite's position it inherits the same wall as every gradient method: the position is a discrete step set by strobe timing, so the underlying gradient is zero and multiplying by the input cannot create signal where there is none. The method is popular because it keeps the speed of a gradient while adding a contribution interpretation, so it is a fair, stronger member of the gradient family to test.

The idea in plain words

Vanilla saliency answers one question: how sensitive is the output to each input? That is useful, but it ignores how big the input actually is. A pixel can be very sensitive and still be black (value 0). Then it contributes nothing to the score right now. Gradient×Input fixes this by multiplying the two: the attribution of input \(i\) is its gradient times its own value. The result reads as “how much of the output this input is responsible for, at the value it has”.

DeepLIFT (Deep Learning Important FeaTures) generalises the idea. It picks a reference (or baseline) input that means “nothing there”, for example an all-black image. It then splits the difference between the output at the real input and the output at the reference among the inputs. The pieces add up exactly to that difference. This property is called completeness (DeepLIFT calls it “summation-to-delta”). With an all-zero reference and a linear model, DeepLIFT and Grad×Input give the same numbers. That is the setting we use on the Atari.

How it works on a neural network

As in vanilla saliency, write the network as \(y = f(x)\). Grad×Input and DeepLIFT (rescale rule) assign input \(i\)

\[ A^{\text{G}\times\text{I}}_i = x_i\,\frac{\partial f}{\partial x_i}(x), \qquad A^{\text{DL}}_i = (x_i - x^0_i)\; m_i ,\]

where \(x^0\) is the reference and \(m_i\) is a multiplier. For a linear unit \(m_i = \partial f/\partial x_i\). Through a nonlinearity such as a ReLU, the rescale rule uses the finite slope \(m = \Delta \text{out}/\Delta \text{in}\) between reference and input instead of the infinitesimal one. The product of input and gradient is the first-order Taylor term \(\nabla f(x)\cdot x\): for a linear function with zero bias it is exactly \(f(x) - f(0)\).

Toy example 1 (linear). Let \(f(x) = 2x_1 - x_2 + 0.5x_3\) at \(x = (4, 1, 0)\). The gradient is \((2, -1, 0.5)\). Saliency says \(x_1\) matters most, then \(x_2\), then \(x_3\). Grad×Input gives \((8, -1, 0)\): \(x_3\) gets zero, because it is switched off. The sum is \(8 - 1 + 0 = 7 = f(x) - f(0)\). Completeness holds.

Toy example 2 (nonlinear). Let \(f(x) = x^2\) at \(x = 3\), reference \(x^0 = 0\). The gradient is 6, so Grad×Input says 18. But the output only changed by \(f(3) - f(0) = 9\). DeepLIFT's rescale multiplier is \((9 - 0)/(3 - 0) = 3\), giving \(3 \cdot 3 = 9\): complete. So Grad×Input is complete only for linear pieces; DeepLIFT repairs this by using finite differences.

Recipe

  1. Pick the input \(x\), the scalar output \(y\), and (for DeepLIFT) a reference \(x^0\). The usual default is all zeros.
  2. Compute the gradient \(\partial y/\partial x_i\) with one backward pass, exactly as in vanilla saliency.
  3. Multiply element-wise: \(x_i \cdot \partial y/\partial x_i\) (Grad×Input) or \((x_i - x^0_i)\cdot m_i\) (DeepLIFT).
  4. Optionally check completeness: \(\sum_i A_i\) should equal \(y(x) - y(x^0)\).
  5. Keep the sign (positive = pushes the output up) or take \(|A_i|\) for a heat-map.

How we apply it to the VCS

The runner computes three maps from one gradient: Grad×Input \(u \odot \partial y/\partial u\), DeepLIFT \((u - 0)\odot \partial y/\partial u\), and vanilla saliency \(|\partial y/\partial u|\) as the contrast. Here \(u\) is the RAM vector. Because the reference is all zeros, the first two are identical. The record's headline number is the DeepLIFT correlation with the oracle.

  • Content output. \(y\) is soft_ram_peek(ram, s), a one-hot dot product. Its gradient is the one-hot vector \(e_s\), so Grad×Input is a single spike of height \(u_s\) at byte \(s\). Completeness is exact: \(\sum_i A_i = u_s = y(x) - y(0)\). The runner checks this numerically. Note what the input factor can and cannot do here: it only rescales the one spike saliency already had. The ranking of causes is unchanged, unless \(u_s = 0\). Then the attribution vanishes entirely.
  • Choosing the byte. That last case is why select_content_cell refuses a zero byte. It also tests each candidate on the real VCS: poke it to value+17, run 15 frames, and keep only bytes whose own change survives to the readout. Otherwise the game could overwrite the poke within the horizon and leave an all-zero oracle map. A score byte is preferred when it qualifies.
  • Position output. The naive gradient is exactly zero, because sprite positions are set by strobe timing (see vanilla saliency). The runner therefore takes the gradient through the bilinear sampler, which slides a sprite footprint along a continuous column driven by one position byte. Grad×Input multiplies that gradient by the position byte's value. If the byte happens to be 0, the restored gradient is wiped out again. This is a real failure mode the runner records, not a bug.
  • Scoring. Each map is turned into one number per oracle cause (\(|A|\) at that RAM byte; 0 for TIA-register and joystick causes the RAM map cannot see). It is compared with the oracle by Pearson/Spearman correlation and precision@3, and by deletion/insertion curves that re-run the real ROM. A positive control scores the oracle against itself.
  • End-to-end variant. e2e_gradient.jl also multiplies its through-the-machine gradient (see vanilla saliency) by the RAM at \(f^*\). It reads the content byte the saliency runner uses and has no non-zero guard. So the failure mode above shows up for real. In Seaquest that byte holds 0 at \(f^*\), and the e2e Grad×Input score is exactly 0, while the e2e saliency on the same gradient scores 0.017. The same happens for Q*bert's position output.

Reading the result

Compare the Grad×Input bars with the vanilla saliency page. On the content output both show one spike at the same byte; Grad×Input's spike is just taller or shorter, scaled by the byte's value. So its agreement with the oracle tracks saliency closely. A one-byte map can only partly match an oracle that lights up several causes over 15 frames. On the position output, expect much weaker agreement: the sampler restores a gradient, but it points at one byte, and that byte is not always the one the oracle ranks first. Completeness holds exactly on content, yet it does not make the map more faithful. Summing to the right total says nothing about whether the total is split among the right causes.

Pitfalls

  • Zero inputs get zero credit. A byte (or pixel) whose value is 0 receives no attribution, however important it is. On the VCS many flags and counters are legitimately 0.
  • Reference dependence. The all-zeros reference is a choice, not a law. Kindermans et al. showed that shifting every input by a constant changes Grad×Input/DeepLIFT maps although the model's decisions do not change.
  • Completeness is not faithfulness. Attributions can sum to the exact output change and still be assigned to the wrong inputs. On the content read here it is complete by construction because the read is linear.
  • Inherits every gradient problem. Multiplying by the input cannot create a gradient where there is none. The naive position gradient stays zero; only the sampler gives the method something to multiply.

How it's scored

The score is the Pearson correlation of the Grad-times-Input, DeepLIFT-style attribution with the oracle's exact causal map, reported raw. Faithfulness for this method is that correlation, and the grading is always against the intervention oracle rather than another method. Multiplying the gradient by the input concentrates the attribution onto the genuine causal byte, so on smooth content outputs it improves on plain saliency and scores well. The hard case is the same as for the whole gradient family. A sprite's position is a discrete step set by strobe timing, so the naive gradient there is provably zero, and multiplying a zero gradient by the input is still zero. The audit turns on the differentiable sampler to give the method a fair chance on position, but the restored gradient is faithful on only a minority of games, so the position score stays low while the content score stays high. The completeness property, that attributions sum to the output change, does not rescue the position regime. The audit box reports the all-regime faithfulness, which averages the strong content result and the weak position result across the 44 scored games, so the single number sits between the two.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack. How each of F / S / M is actually computed for this method (and whether it matches the paper) is in the box just below; the numbers are in the In the audit box under it.
