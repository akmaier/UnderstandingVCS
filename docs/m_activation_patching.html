Activation patching / causal mediation

Vig et al. 2020; ROME, Meng et al. 2022

← back to the method catalogue

What it does?

Activation patching, also called causal mediation, is a core mechanistic-interpretability method. It runs the system once, records an internal value, and then, on a second run, overwrites, or 'patches', that internal value with the one recorded from a different input. The change in the output measures how much that internal value causally mediates the behaviour. In language-model work this is how researchers localise where a fact or a computation lives inside the network. The idea is genuinely causal: it does not correlate, it substitutes a value and observes the effect. We apply it to the VCS by patching a recorded state value, a RAM cell or register, from one run into another and measuring the causal effect on the output. On this machine the operation is special. Clamping a cell to a donor value and re-running the real ROM is literally the same operation the intervention oracle performs. So activation patching cannot disagree with the oracle: it recovers the exact causal-effect table by construction. This makes it the clearest demonstration that where a method's operation is itself a real intervention on a fully observable machine, faithfulness is automatic. The catch, taken up elsewhere, is that recovering the exact effect table is still not the same as recovering what the patched variables mean.

The idea in plain words

Gradient methods ask “what if I nudged this a tiny bit?”. Activation patching asks a bolder, causal question: what if this internal value had been the one from a different input? You run the network twice. The clean run uses the input you care about (“The Eiffel Tower is in” → “Paris”). The corrupted run uses a slightly different input that gives a different answer. Then you run a third time, and at one chosen place inside the network you overwrite (“patch”) the internal value with the one recorded in the other run. If the answer flips, that place carries the information that decides the answer.

An internal value of a network is called an activation: the output of one neuron, one layer or one attention head. Statisticians call a variable that sits on the causal path from cause to effect a mediator, so the method is also called causal mediation analysis. It is the workhorse of mechanistic interpretability, the attempt to reverse-engineer the algorithm a network runs. Unlike a correlation, a patch is an intervention: it sets a value and watches what happens. On the VCS we can do exactly the same thing to the machine's memory, and it turns out to be identical to our ground-truth oracle.

How it works on a neural network

Let \(x\) be the clean input and \(\tilde x\) the corrupted one. Let \(a_\ell(x)\) be the activation of component \(\ell\) (a neuron, an attention head, or a position in the residual stream: the running vector that every transformer layer reads from and adds to). Write \(y(x \mid a_\ell := v)\) for the output when we run on \(x\) but force \(a_\ell\) to the value \(v\). The patch effect of component \(\ell\) is

\[ \Delta_\ell \;=\; y\big(x \,\big|\, a_\ell := a_\ell(\tilde x)\big) \;-\; y(x). \]

This direction (corrupted value into the clean run) is called noising; the reverse (clean value into the corrupted run) is denoising. In ROME’s “causal tracing” the corruption is Gaussian noise on the subject tokens, and the patched-back clean state shows where a fact is recalled. Each \(\Delta_\ell\) costs one extra forward pass.

Toy example. Take a two-step network \(h = 2x_1\), \(g = x_2 + 1\), \(y = h + 3g\). Clean input \(x = (1, 0)\) gives \(h = 2\), \(g = 1\), \(y = 5\). Corrupted input \(\tilde x = (4, 0)\) gives \(h = 8\), \(g = 1\), \(y = 11\). Patch \(h\): run on \(x\) but set \(h := 8\). Then \(y = 8 + 3 = 11\), so \(\Delta_h = 6\): \(h\) mediates the whole difference. Patch \(g\): its corrupted value is also 1, so \(\Delta_g = 0\). The patch tells us which component carries the change between these two inputs, not which components matter in general. A different \(\tilde x\) (say, changing \(x_2\)) would light up \(g\) instead.

Recipe

  1. Choose a clean input and a corrupted input that differ in the one thing you study, and a scalar metric (a logit difference, a probability).
  2. Run both and cache every activation you might patch.
  3. For each component \(\ell\): re-run the clean input, overwrite \(a_\ell\) with its cached corrupted value, let the rest of the network compute normally.
  4. Record \(\Delta_\ell\), the change in the metric, often normalised by the full clean-vs-corrupted gap.
  5. Plot \(\Delta_\ell\) over layers and positions: the bright cells are the candidate mediators.

How we apply it to the VCS

The runner sits on the shared testbed that every method uses: a seeded stream of random joystick actions, a checkpoint at frame \(f^*\), and a horizon of 15 frames. Two fresh boots are first asserted to be byte-identical in RAM and screen, so any later difference is caused by our patch and nothing else.

  1. Outputs. The runner picks the two candidate RAM bytes whose own value moves most under the oracle’s interventions, and adds a whole-screen output: the count of pixels that differ from the clean final frame.
  2. Donor patches. Two donor runs share the gameplay prefix and press LEFT or RIGHT just before \(f^*\). For every candidate byte the donor’s value is written into a copy of the clean checkpoint. The record notes whether the donor actually differed there; equal values are honest no-op patches.
  3. Directed patches. Because a one-frame donor leaves many bytes unchanged, every candidate byte is also patched to base+17 (the same value the oracle uses), plus one TIA patch that sets the background colour to white.
  4. Recovered vs exact. Each patch is re-run on the clean checkpoint (the method). The same write is then replayed from an independent fresh boot (the oracle). The two effect tables are compared cell by cell. They are equal, because both are the same single-site write followed by the same deterministic program.
  5. Edge precision/recall. A (patch, output) pair “fires” if its effect is non-zero. The recovered firing pattern is scored against the exact one. An honest extra audit lists transient sites: bytes the program overwrites on the next frame, so their patch never reaches the outputs.

The difference from LLM practice is worth stating plainly. In a transformer, patching and “the truth” are different things, and we argue about which metric to trust. On the VCS, patching a byte and re-running is the oracle’s own definition of a cause. So this method is the reference the other Phase C methods approximate.

Reading the result

The headline number is the largest gap between the recovered and the exact effect table. Expect it to be zero on every game: this is a positive result by construction, not a discovery. The more informative parts are the firing pattern and the transient list. Many bytes show no effect because the game recomputes them every frame. Others move a score byte but not the screen, or the reverse. Read the page as a map of which variables mediate which outputs over 15 frames, not as a test the method could fail.

Pitfalls

  • The answer depends on the corruption. A patch measures what carries the difference between these two runs. A donor that does not change a byte can never reveal that byte, which is why we add directed patches.
  • Off-distribution values. A directed value like base+17, or Gaussian noise in ROME, may put the system in a state it never visits naturally. The effect is real, but it may not describe normal behaviour.
  • Effect is not meaning. A perfect effect table says which byte matters, not what it represents or how bytes combine. Hase et al. also found that where patching localises a fact is a poor guide to where editing it works.
  • Metric choice changes the picture. Zhang & Nanda show that logit difference, probability and noising vs denoising can rank components differently in LLMs.
  • Cost. One full re-run per site and value. Fine for 128 bytes, expensive for billions of activations; this is what attribution patching tries to fix.

How it's scored

The score is the maximum absolute difference between the recovered patch effect and the exact patch effect from the oracle, taken across every site and every core game. The grading is always against the intervention oracle. This method is exact by construction, so the difference is zero. Clamping a cell to a donor value and re-running the real ROM is literally the same operation the intervention oracle performs, so the recovered effect table cannot disagree with the oracle, and site precision and recall are both perfect. Faithfulness for this method is therefore at the ceiling, level with the oracle-as-method positive control. There is no sprite-position hard-case here: because the method intervenes on the real machine rather than taking a derivative, it works on position outputs exactly as it works on content outputs. The important qualification, which the score does not by itself capture, is that recovering the exact effect table is not the same as recovering what the patched variables mean or how they combine into the computed function. The audit box reports the measured triad. This method is the clearest demonstration that when a method's operation is itself a real intervention on a fully observable machine, faithfulness is automatic.

The score is measured against the §1 intervention oracle — never against another interpretability method. F (faithful) is always vs the oracle; see the execution stack.
